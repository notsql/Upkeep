# Object storage on Google Cloud Storage

**Status:** draft
**Owner:** Ong Zheng Kai

## Problem

Documents, inspection photos and fault-report photos are stored in Cloudflare
R2 through its S3 emulation (`software.amazon.awssdk:s3`). Three classes -
`document/DocumentStore`, `inspection/InspectionImageStore` and
`resident/ResidentImageStore` - each build and configure their own `S3Client`,
so the same connection, error and "not configured" code exists three times.
SDK types leak past the stores: `DocumentStore.list()` returns
`ListObjectsV2Response`, which `DocumentService` reads directly. Tests stub
the S3 client by hand in two different ways.

The API already runs on Cloud Run under a GCP service account
(`vars.GCP_API_RUNTIME_SA`, `.github/workflows/deploy.yml`), yet production
receives no storage credentials at all today, so storage is effectively off
in `prd`. Google Cloud Storage can be reached with that identity and no
long-lived keys, removing a second cloud provider and its secrets.

## Behaviour

Storage port

- There is exactly one storage abstraction, `ObjectStorage`, in
  `com.proj.server.storage`, with operations: put (key, bytes, content type),
  get (key -> bytes and content type, or "not found"), delete (key), and list
  by prefix (-> key and last-modified time per object).
- No type from a storage SDK (AWS or Google) appears in any class outside
  `com.proj.server.storage`.
- There is exactly one production implementation, backed by Google Cloud
  Storage; no class in the server builds an `S3Client`.
- `DocumentStore`, `InspectionImageStore` and `ResidentImageStore` either use
  `ObjectStorage` or are removed in its favour; none holds its own client.
- Object keys are unchanged: `documents/{estateId}/{uuid}`,
  `inspections/{inspectionId}/{imageId}`, `reports/{reportId}/{imageId}`, all
  in one bucket.

Configuration and credentials

- The bucket is read from `app.storage.bucket`, bound to `GCS_BUCKET_NAME`.
  `app.storage.project-id` (`GCS_PROJECT_ID`) is optional; when blank the
  project comes from Application Default Credentials.
- Credentials come only from Application Default Credentials: the Cloud Run
  runtime service account in production; locally
  `GOOGLE_APPLICATION_CREDENTIALS` or `gcloud auth application-default login`.
  No access key or secret is configured.
- The `app.r2.*` properties and the `S3_ENDPOINT`, `R2_ACCESS_ID`,
  `R2_SECRET_ACCESS_KEY` and `R2_BUCKET_NAME` variables no longer exist.
- With a blank bucket the app starts, and storage is "not configured".

Unchanged behaviour (each is an existing test that must still pass)

- Uploading a document, inspection photo or report photo writes the object
  first and commits the database row second; if the commit fails, the object
  is deleted.
- Downloads stream the stored bytes through Spring with the stored content
  type and `Cache-Control: private, no-store`.
- When storage is not configured or unavailable, uploads and downloads answer
  503 "storage temporarily unavailable"; deletes and sweeps are no-ops.
- Hourly sweeps list each prefix and delete objects older than 24 hours with
  no matching row; objects younger than 24 hours are kept.
- Durable deletion (decision 0036) is unchanged: the soft-delete marker is
  written first, the object deleted second, and `storageDeletedAt` set only
  after the object delete succeeds; a failed object delete is retried later.
- Getting a key that does not exist is "not found", not 503.

Tests

- One in-memory `ObjectStorage` fake replaces `DocumentR2Stub`, the inline
  S3 stub in `InspectionPhotosIntegrationTests` and the Mockito mocks of
  `ResidentImageStore`, and is shared through test support.
- The fake can be switched to `unavailable` (all operations fail) and
  `deletionUnavailable` (only delete fails), covering the same failure paths
  as today.
- The GCS implementation is not exercised against a real bucket or an
  emulator container in the test suite.

Dependencies and deploy

- `software.amazon.awssdk:s3` is removed from `apps/server/pom.xml`;
  `com.google.cloud:google-cloud-storage` is added, versioned by importing
  `com.google.cloud:libraries-bom` in `dependencyManagement`. A human adds
  and resolves these (AGENTS.md rule 1).
- `deploy.yml` passes `GCS_BUCKET_NAME` to `upkeep-server-prd`.
- The production bucket is private: uniform bucket-level access, public
  access prevention enforced, no public ACLs.
- The runtime service account has `roles/storage.objectAdmin` on that bucket
  only, not project-wide.
- R2 secrets are removed from Infisical, `.env.example` files and docs.

## Edge cases

- Bucket set but ADC missing or lacking permission: operations fail as
  "unavailable" (503 / retry later), the app still starts.
- Listing a prefix with more objects than one page returns: the port pages
  through all of them, so sweeps see every object.
- Content type absent on a stored object: download falls back to
  `application/octet-stream`, as today.
- Deleting a key that is already gone counts as success, so durable deletion
  completes.
- Rows referencing objects that exist only in R2 return "not found" after the
  switch, since data is not migrated (see Out of scope).

## Out of scope

- Migrating existing R2 objects to GCS. If wanted later, it is a one-off
  manual `rclone`/`gsutil` copy, not code in this repo.
- Signed URLs or direct browser upload/download; Spring keeps proxying.
- A GCS emulator in tests or local dev.
- Per-feature buckets, lifecycle rules, CDN or object versioning.
- Provisioning the bucket and IAM binding with Terraform or scripts; a human
  does it once in the console or with `gcloud`.

When built, record the switch in
`.spec/decisions/0050-object-storage-moves-to-gcs.md` (not written yet).
