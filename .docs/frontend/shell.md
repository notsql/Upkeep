# App shell (frontend)

Assets opens for `canViewAssets || canViewAssetHistory || canViewInspectionResults`.
The shared `_auth` guard admits Council profile/History deep links independently
of private asset sections; see [asset-history.md](asset-history.md).

The root layout, header, home page and the conventions every feature file
below relies on. Paths are relative to `apps/web/src/`.

## Bootstrapping

| File | Role |
| --- | --- |
| `start.ts` | TanStack Start instance. Request middleware: CSRF (server functions only), then `authkitMiddleware()`. |
| `router.tsx` | `getRouter()` builds a **new `QueryClient` per router** (never module scope - SSR must not share caches). Default query `staleTime` 60s. Pending component `RoutePending` (`components/states/route-pending.tsx`: header + `LoadingState` skeleton, `role="status"` named "Loading page…", `animate-in fade-in`), rendered inside `AppShell`'s outlet so the sidebar and header stay mounted; `defaultPendingMs` 200, `defaultPendingMinMs` 300, `defaultPreload: "intent"` (hover/focus runs guards early). `/` uses `HomePending` (header, three stat-card skeletons, list rows; "Loading your workspace…"); not-found renders `NotFoundPage`. Router context: `{ queryClient }`. |
| `routes/__root.tsx` | `<html>` document. Provider order: `ThemeProvider` (next-themes, class, default `light`) > `AuthProvider` > `QueryClientProvider`. Layout: `AppShell` wraps `<Outlet />`. Signed-in users get the shadcn `Sidebar` (a collapsible rail on desktop, a sheet opened from the top-bar trigger on mobile) and a compact top bar; public pages get the public header only. Also mounts `Toaster` (`@proj/ui/components/sonner`, `richColors`) and router devtools. |
| `routeTree.gen.ts` | Generated by the TanStack router plugin. Never edit. |

## Routes

ID-60 adds `/estates/$estateId/readings`, checked before general management
fallbacks using `canViewReadings`. Owner/Manager/Crew may browse; unavailable
estate/role URLs render Page not found. Switching estates preserves Readings
when permitted. See [readings.md](readings.md). `/readings/$assetId` (that asset's readings) shares that gate. There are no
manual-entry routes. `?assetId=` on `/readings` redirects to the path form.

Retired pages redirect in their route's `beforeLoad` (`replace: true`), and
the `_auth` guard then checks the destination: `/devices`, `/sensors`,
`/sensors/all` -> `/assets/devices`; `/failure-risk` -> `/assets`.

| File | URL | Guard | Screen |
| --- | --- | --- | --- |
| `routes/index.tsx` | `/` | none | Signed out: public `HomePage` (`routes/-components/home-page/home-page.tsx`, composing `home-no-workspace.tsx`, `home-sign-in-card.tsx` and `home-feature-cards.tsx`). Signed in: redirects (below), except resident-only accounts, who get `ResidentDashboard` (see [resident-dashboard.md](resident-dashboard.md)). |

The public home content has one Create account action and a secondary System
status card (`useHealth()` from `lib/health.ts`: key `["health"]`,
`GET /health`). The header omits Register and uses the same Sign in wording.

Signed-in `/` awaits Spring access in `beforeLoad` (`getSessionAccess`, seeding
`[userId, "app-access"]`) and decides, in order:

1. resident-only (`hasResidentMembership && !canEnterWorkspace`): no redirect;
   `HomePage` renders `ResidentDashboard`;
2. report-only (a `canViewFaultReports` estate, no `canViewManagement` estate):
   `/estates/<id>/reports`;
3. roles/invitations-only: `/estates/<id>/roles` or `/estates/<id>/council`;
4. exactly one membership (`access.estates.length === 1`): that estate's
   `estateDestination(estate, "management")`;
5. otherwise (0 or 2+): `/estates`.

`HomePage` still has an unassigned-account branch (no workspace, not resident
only): PageHeader "Report a fault" (`icon={LayoutDashboard}`, so the button's ClipboardPenLine is not repeated; "Create an estate
or accept an invitation"), a primary "Report a fault" and, with
`canCreateEstate`, an outline "Create estate" (Plus). The public home header
uses `icon={LayoutDashboard}` ("Estates, equipment and council access"); the
System status title has a HeartPulse icon (`text-brand-2`). the feature cards show their icons in `bg-brand-1/15 text-brand-3` tiles. The active sidebar item uses `sidebar-accent` with its icon in `text-sidebar-primary` (`DestinationLink`). A failed access lookup on home is `ErrorState` + Retry. There is
no portfolio dashboard; `/estates` is the single "All estates" landing
(directory + pending invitations, see [estates.md](estates.md)).

## Shell and navigation

`components/shell/app-shell.tsx` renders a skip-to-content link (an `<a>` styled with
`buttonVariants`, `sr-only focus:not-sr-only`) as the first focusable element,
targeting the focusable `#main-content` wrapper. Route screens own their main
landmark (`PageLayout`, a `<main>`), so the shell uses a plain flex `div`
instead of `SidebarInset`. Without a sidebar the shell is skip link + `Header` +
content. With one it is `SidebarProvider` > `AppNavigation` + a column holding
`Header` and `#main-content`. The provider is held open (`open` with a no-op
`onOpenChange`), so the desktop sidebar cannot be collapsed (no trigger, and
Cmd/Ctrl+B does nothing). On mobile the header gets `SidebarTrigger` as `start`
and keeps the brand; on desktop the header omits the brand (`brand={false}`)
because the sidebar shows it.

The sidebar is shown, signed in, when `hasSidebar(pathname, residentOnly)` (in
`components/shell/app-navigation.tsx`) is true: `/estates/$estateId/**` (id not
`new`), `/reports` and `/reports/**`, and `/` for resident-only accounts. It is
not shown on `/estates`, `/estates/new`, `/account`, `/admin/**`,
`/invitations` or the staff `/`.

### Header

`components/shell/header.tsx` is sticky and identical on mobile and desktop. Left:
optional `start` slot (the mobile `SidebarTrigger`), the "UpKeep" brand link to `/`
(inside `<nav aria-label="Header navigation">`; omitted when `brand` is false),
and, when signed in, a "/" separator (only with the brand) then the **estate switcher**. Right: `ThemeToggle` and `AuthButton`.

The switcher is `components/shell/estate-feature-switcher.tsx` (shadcn
ghost `Button` + `DropdownMenu`), used directly; the old
`EstateContextSwitcher`, `WorkOrderEstateSwitcher`, `ReportEstateSwitcher` and
`EstateFeatureChooser` wrappers are deleted. The header derives `feature` from
the pathname: `/reports/new` -> `report-creation`, other `/reports*` ->
`resident`, `/estates/<id>/<reports|work-orders|documents|readings>` -> that
section, else `management`. It lists every `access.estates` entry for
`canEnterWorkspace` accounts and only `RESIDENT` memberships otherwise.

- Trigger: current estate name + role label (Manager, Crew, Council, Member,
  Resident or custom-role name). Outside an estate (`/estates`,
  `/estates/new`, `/account`, `/admin/users`, `/invitations`), or when the URL
  estate is not accessible, it reads **"Select estate"**; disabled until
  access context loads.
- Menu: each estate with role and a check on the current one; inactive
  Resident choices disabled with "Reporting unavailable" (from
  `residentEstates`); separator; "All estates" -> `/estates`; "Create estate"
  -> `/estates/new` only when `canCreateEstate`. Height caps at
  min(20rem, available height) with internal scrolling.
- Current estate comes from the URL only (`useCurrentEstate()` in
  `app-navigation.tsx`): the `/estates/<id>` segment, or on resident pages the
  `estateId` search param, else the sole resident estate. No storage.
- Choosing an estate goes to `estateDestination(estate, feature)` from
  `lib/estate-destinations.ts`: stay on the same feature when permitted, else
  overview, else work orders / fault reports / documents / roles / council,
  else `/estates`; Residents go to `/reports` or `/reports/new` with
  `estateId`. Choices come from `GET /access/context` (`[userId, "app-access"]`).

`AuthButton` (`components/auth/auth-button.tsx`) is a circular profile button with a
shadcn `DropdownMenu`: email label, "Account settings" -> `/account`,
"Admin users" -> `/admin/users` only when `canAccessPlatformAdmin`, "Sign out"
-> `/logout`. Nothing else; it is the only place to sign out.

`components/shell/theme-toggle.tsx` is a shadcn Button using next-themes (light
default, label names the next mode, disabled before mount).

### Sidebar (estate scope)

`AppNavigation` renders the shadcn `Sidebar`: `SidebarContent` with
`<nav aria-label="Sidebar">`, then a `SidebarFooter` tagline ("Your estates,
organised."). A `SidebarHeader` at the top holds the brand: an icon tile plus
"UpKeep", linking to `/` (outside the Sidebar nav). No switcher, no "Workspace" group, no cross-estate
entries. Labelled groups are `SidebarGroup role="group"` with an `aria-label`;
a group with no visible items is not rendered.

| Group | Item | Route under `/estates/$estateId` | Predicate (`lib/estate-destinations.ts`) |
| --- | --- | --- | --- |
| (unlabelled) | Overview | `` (exact match) | `canOpenOverview`: `canViewEstateDetails ?? canViewManagement` |
| Operations | Work orders | `/work-orders` | `canOpenWorkOrders`: `canViewWorkOrders` |
| Operations | Fault reports | `/reports` | `canOpenFaultReports`: `canViewFaultReports` |
| Operations | Inspections | `/inspections` | `canOpenInspections`: `owned \|\| canManageInvitationPermissions` |
| Assets | Locations | `/locations` | `canViewManagement` |
| Assets | Assets | `/assets`, or `/assets/devices` | `assetsEntry`: `/assets` when `canOpenAssets` (`canViewAssets \|\| canViewAssetHistory \|\| canViewInspectionResults`), else `/assets/devices` when `canOpenAllDevices`, else hidden |
| Records | Documents | `/documents` | `canOpenDocuments`: `canViewDocuments` |
| Administration | Members | `/council` | `canOpenMembers`: `canViewEstateInvitations \|\| canInviteMembers \|\| canManageInvitationPermissions` |
| Administration | Roles | `/roles` | `canOpenRoles`: `canViewEstateRoles` |
| Administration | Asset categories | `/asset-categories` | `canOpenAssetCategories`: `owned \|\| canManageInvitationPermissions` |
| Administration | Estate settings | `/edit` | `canOpenEstateSettings`: `owned \|\| canManageEstate` |

There is no Devices, Readings, Device monitoring or Failure risk item: those
pages live under Assets (All devices, the asset Overview, By location's risk
column). No screen links to `/readings` any more (the "All readings" link was
removed from the Assets views); it is reachable by URL only;
Crew reach an asset's readings from a work order's "View readings" / "Record
reading" links (see [work-orders.md](work-orders.md)).

`owned` comes from `useEstate(estateId)` (`EstateResponse.owned`, key
`["estates", userId, "details", estateId]`), mounted only when
`canViewManagement`; owner-only items stay hidden until it resolves. Access
loading or errored: no items. Role- or invitation-only estates show only
Administration > Roles/Members.

Active state: an item is active when its route equals or prefixes the pathname
(nested pages keep their section), Overview by exact match; active links get
`isActive` and `aria-current="page"`. Links use
`activeOptions={{ exact: true, includeSearch: false }}`; icons are
`aria-hidden`.

At >=768px the sidebar is always open, with no toggle. Below 768px
(`@proj/ui/hooks/use-mobile`) the same sidebar opens as a `Sheet` from the header
`SidebarTrigger` ("Toggle Sidebar") and closes when a link is followed. There is **no separate mobile
navigation**: `EstateNavigation` and `components/estate-section-menu.tsx` are
deleted, and there is no bottom bar.

### Shared destination predicates and guards

`lib/estate-destinations.ts` exports one pure `canOpen*` function per sidebar
row (inputs: the `EstateAccessResponse`, optional `owned`, optional
`canAccessPlatformAdmin`), plus `estateDestination` and the `EstateFeature`
type. The sidebar and `routes/_auth/route.tsx` both import them; neither
restates a rule (see `.spec/decisions/0043-*`).

In `_auth/route.tsx`, `guardDestination` handles the section-level URLs
(exactly `/estates/<id>/<section>`):

- `/assets` (list) 404s unless `canOpenAssets`. Asset children
  (`/assets/$assetId/**`) keep `guardInspectionContext`.
- `/assets/devices` (All devices) is matched first (`isAllDevicesPath`, so
  "devices" is never treated as an asset ID by `guardInspectionContext`) and
  uses `canOpenAllDevices` (`canOpenDevices || canOpenSensors`), loading
  ownership like the owner-gated sections: owner, Manager and Council open it
  without `canViewAssets`; Crew and inspection-only readers get `notFound()`.
- `/asset-categories`, `/inspections`, `/edit` use `OWNER_GATED`
  predicates. If access flags alone
  do not open the page, the guard loads ownership with
  `queryClient.ensureQueryData` on `["estates", userId, "details", estateId]`
  (server function `getSessionEstate`, i.e. `GET /estates/{id}`); a failed
  fetch counts as not owned. Otherwise `notFound()`. There is no fallback to
  `canViewManagement`.

`components/states/not-found-page.tsx` is the router's default not-found screen, with
PageHeader (`icon={SearchX}`, "Moved or mistyped address") and a Go to home
link with a House icon.

See [design-system.md](design-system.md) for tokens, layouts and the page
header convention.

## Resident reporting context

`components/shell/resident-navigation.ts` builds the resident sidebar (one
unlabelled group) when the current estate is a `RESIDENT` membership, from
access context only:

- "Dashboard" -> `/` with `estateId`, only when `!canEnterWorkspace` (mixed
  resident + staff accounts follow the staff `/` redirect, so it is hidden);
- "Report a fault" -> `/reports/new?estateId=`, only when the estate is in
  active `residentEstates`;
- "My reports" -> `/reports?estateId=`, active on `/reports` and
  `/reports/$reportId`.

The resident sidebar shows on `/` (resident-only), `/reports`, `/reports/new`
and `/reports/$reportId`. Residents never get the estate sidebar; estate
routes still redirect a `RESIDENT` membership to the resident area. Mixed
accounts on `/reports` see the resident sidebar for the selected resident estate
while the switcher lists all estates. Historical own-report URLs and API
authorization are unchanged.

## Conventions used by every feature

Manager/Crew report navigation is documented in [estate-reports.md](estate-reports.md).
Estate report routes use `canViewFaultReports` independently of management
capabilities. Crew-only accounts land on assigned reports and switch report
estates by name through access context; management estate queries are not mounted
for their report navigation. Report estates are switched from the header switcher.

- **API client:** `lib/api.ts` exports `api` (`createApiClient` from
  `@proj/api`, base URL `VITE_API_URL`). The bearer token is resolved per
  request by `AuthTokenBridge` (browser only; SSR requests go unauthenticated).
- **Hooks live in `lib/<feature>.ts`.** Screens call those hooks. Exceptions
  that still call `api` inline are noted per feature (estate create/edit/
  deactivate, location writes, admin screens).
- **Session gate:** `useEstateSession()` (`lib/estates.ts`) returns
  `{ userId, ready }`; `ready` is true only after mount, once AuthKit has
  finished loading and a user exists. All estate-scoped queries use
  `enabled: ready` and `retry: false`.
- **Query keys** for per-user data start `["estates", userId, ...]`, so
  invalidating `["estates", userId]` clears one user's estate cache.
- **Errors:** `estateError(error, status)` turns an API error into an `Error`
  (401 gives a "sign in again" message, 5xx messages containing SQL/exception details get generic retry feedback; other messages preserve the API's `message`). Screens show `query.error.message` in a labelled alert (shadcn Alert or existing role="alert" text).
- **Loading:** visible text in a `role="status"` (or `aria-live`) paragraph
  with a decorative shadcn `Spinner` (`aria-hidden`), so only the text is
  announced.
- **Status pills:** stock shadcn `Badge` variants only, with the state always in
  the label text. LifecycleStatusBadge: Active `default`, Inactive/Retired
  `destructive`. ConditionBadge: Good `default`, Needs attention `secondary`,
  Faulty `destructive`, Not assessed yet `outline`. Estates uses shadcn `Empty`; other features retain descriptive empty text.
- **Success feedback:** `toast.success(...)` from `sonner`.
- **Forms:** feature-local state/FormData, existing shadcn Input/Select/Checkbox/
  Textarea and Label (or Field where already used), disabled fieldsets while
  pending, optional-field labels and retained inputs after errors. Asset form
  errors are linked using aria-invalid/aria-describedby. Estate/asset editors
  share FormActions for Save/Cancel. Location/assessment forms use dialogs and
  device registration has its own page; email invitations remain inline. Server validation and payloads are unchanged.

### Browser tab title

Every tab title is `UpKeep`, or `UpKeep · <Page>` when a route names a page (app name first, middle dot separator). `src/lib/page-title.ts` owns the format: `__root.tsx` sets the default with `pageTitle()`, and each route sets `head: () => pageHead("<Page>")` (e.g. `pageHead("Work orders")` -> `UpKeep · Work orders`). Never write a `title` meta by hand. Tested in `tests/lib/page-title.test.ts`.

## Test imports

The web tsconfig maps `@/*` to `src/*` and `@tests/*` to `tests/*`. Vite and
Vitest use the same native tsconfig path resolution. Tests import application
code through `@/` and can import shared helpers through `@tests/test-utils`.

Work-order capability guards run before general resident/workspace redirects.
Signed-in unauthorized list/detail/create deep links show Page not found without
mounting protected child queries. Normal resident entry and signed-out sign-in
behaviour remain intact.

## Custom estate permissions

Estate-scoped navigation and `_auth` guard check Roles and council capabilities
before requiring management access. Roles requires canViewEstateRoles; council
requires canViewEstateInvitations/canInviteMembers/member-admin authority. Access
lookup failures mount no controls. Role-only and invitation-only users therefore
need no VIEW_ESTATE. AppNavigation avoids useEstate for these contexts and
shows only Administration > Roles/Members; the header switcher labels them from
access estateName. Home sends a scoped-only user to Roles or estate
invitations after checking management/report entry. Access/cache remains per user.
See [estate-roles.md](estate-roles.md) and [council-invitations.md](council-invitations.md).

## Inspection capability routing

The protected guard admits only the estate's exact inspection asset list/detail,
result creation and result detail paths with their inspection capabilities.
Crew estate overview reads use canViewEstateDetails, independent of management
or asset-admin grants. Sidebar Assets includes authorised inspection readers;
work-order creation uses its separate capability, now also available to Crew.
Restricted views never mount owner-only asset hooks. See
[inspections](inspections.md) for generated-client requests and cache handling.
