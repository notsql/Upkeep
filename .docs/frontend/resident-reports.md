# Resident reporting screens

All routes nest under `apps/web/src/routes/_auth/reports/`. The `_auth` `beforeLoad` authenticates report routes without requiring current membership. Management routes await a request-scoped access lookup before any child loader starts. A resident-only account lands on `/reports/new`; mixed accounts retain permitted management deep links in their other estates, while management deep links to their resident estate redirect to reporting. Unassigned accounts see the missing-assignment explanation. My reports navigation is visible only with a current Resident membership, including mixed-role accounts, and is hidden for management-only, platform-admin-only and former-resident accounts on desktop and mobile. Direct history/detail access retains existing authenticated ownership checks.

`lib/access-server.ts` uses AuthKit's session token with a fresh generated API client for each server request, returning profile/access data without tokens. `lib/access.ts` owns `GET /access/context` with key `[userId, "app-access"]`, mounted identity gating and focus refetch. Navigation waits for this projection; mixed accounts see both reporting and management destinations. Target-estate capabilities govern Assets/Council links. JWT resident role claims do not control any reporting UI. Identity changes cancel and remove the previous user's access, report and estate queries; image components revoke their blob URLs.

`apps/web/src/lib/reports.ts` owns all generated-client React Query hooks. Per-user query keys start with the current user ID: `[userId, "resident-context"]`, `[userId, "resident-locations"]`, `[userId, "reports", "list", cursor]`, `[userId, "reports", reportId]`, `[userId, "reports", reportId, "image", imageId]`. Queries are enabled only after mounting with a resolved authenticated identity. Server membership checks control location/submission access; history stays readable by its owner after membership deletion, while its navigation link is hidden. Submission has no automatic retry and invalidates that user's report lists. Detail refetches on window focus. The image hook requests a blob with the authenticated API client; the component creates a local object URL and revokes it when the image or identity changes.

`reports/new/index.tsx` defines the route and page title. Its `-components/` folder contains `new-report-page.tsx` for estate and location loading/error states, `new-report-form.tsx` for form state, validation, image limits, submission and navigation, and `report-location-fields.tsx`, `report-details-fields.tsx` and `report-images-field.tsx` for the labelled form sections and removable selected images.

The new-report screen has one labelled shadcn file `Input` with `accept="image/*"`, `multiple`, and no `capture` attribute. It opens the device's native image chooser; supported mobile browsers offer both existing photos and camera capture there. The application does not force a camera or guarantee a camera option on every browser. Repeated selections accumulate in the same removable list, up to three images. Helper text states the server's JPEG/PNG and 5 MB limits; the broader chooser hint does not change server validation.

The generated request schema describes multipart binary fields as strings, so the hook passes a `FormData` body to `openapi-fetch`, which handles it at runtime. The image response is parsed as a blob. No raw fetch is used.

The create mutation derives its input fields from the generated `CreateIssueReportRequest`, replacing only `images` with browser `File[]`. It sends `title`, `description`, `locationId` and optional repeated `images` in FormData. The form shows the title length limit and preserves entered text after a server rejection. Title and description render as plain React text in history/detail.
